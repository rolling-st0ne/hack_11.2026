# Metabase — источник метрик

На общем дашборде **выручка**, **заказы** и **доля брака** поступают из Metabase OSS. Источник указан на карточках; по нажатию открываются формула, источник, исходный набор, время данных и время получения результата. Остальные показатели используют прежние источники. Отдельной страницы BI нет; старый `#bi` открывает обычный дашборд.

## Доступ с разных устройств

Открыть обычный адрес Docker-приложения на порту 3310. Телефон или другой компьютер в доступной сети использует тот же вход и API. Браузер не обращается к Metabase напрямую, не получает JWT и не зависит от `localhost:3001`. Следующая схема с портами 3000/3001 относится только к отдельному запуску без Docker для разработки.

```text
Браузер на любом устройстве → сервер приложения:3000/api
                                    ↓ ACL и фильтры
                              Metabase:3001
                                    ↓ SQL
                           снимок демоданных SQLite
```

Metabase остаётся на `127.0.0.1:3001` сервера приложения. Это внутренний адрес сервиса, а не требование к устройству пользователя. Доступ извне LAN требует размещения самого приложения/сервиса на доступном хосте; старая опубликованная Sites-версия автоматически не обновляется.

## Docker Compose

Из корня репозитория или `fotoprint/`: `docker compose up -d --build --wait`. Оба файла Compose используют один проект `fotoprint-presentation`. Команда сама запускает Metabase, создаёт случайные учётные данные при первом запуске, подключает SQLite-снимок и настраивает запрос метрик. Node и Java на хосте не нужны. Порт интерфейса задаётся `APP_PORT` (по умолчанию 3310), а локальный `.env` может переопределять его.

В Docker внутренний адрес Metabase — `http://metabase:3000`; порт этого сервиса наружу не публикуется. Том `analytics-data` содержит только производный снимок и подключён к Metabase для чтения. Конфигурация с секретами остаётся в отдельном `app-data`, база H2 — в `metabase-data`. Все тома сохраняются при `down/up`; команда `down -v` удаляет данные. Docker-хранилище отдельно от существующей локальной `.data`.

Подготовка хранилища и health checks задают порядок запуска. Приложение настраивает Metabase до открытия своего порта, повторно используя сохранённые ID и пароли. Нужен один API-процесс на одно хранилище. [Полное описание Compose](README.md#docker-compose--одна-команда).

Контейнерный smoke: `docker compose exec app node scripts/smoke-container.mjs prepare`, затем пересоздание контейнеров без удаления volumes и `docker compose exec app node scripts/smoke-container.mjs verify`. Проверяются HTTP, роли, реальный источник метрик, сохранность CSV, аккаунтов, аудита и настроек. Это не визуальная проверка UI.

## Запуск без Docker

Первичная установка на Apple Silicon, Node.js 22.13+:

```sh
npm run bi:install
npm run bi:start
npm run bi:setup
npm run start:background
npm run address
```

Установщик получает Metabase OSS 0.65.3 и Temurin JRE 25.0.5+8 из официальных источников. Системная Java и Docker не меняются. Metabase может запускаться несколько минут. На других платформах установить Java 25, задать `METABASE_JAVA` и поместить OSS JAR в `.data/metabase/runtime/metabase.jar`.

После изменения кода перезапустить приложение: `npm run stop`, затем `npm run start:background`. Для следующих запусков нужны `npm run bi:start` и `npm run start:background`. Остановка: `npm run bi:stop`, `npm run stop`.

Пароли приложения: `.data/auth/ACCESS.txt`. Администратор Metabase: `.data/metabase/ACCESS.txt`, редактор на сервере — `http://localhost:3001`. Организационная учётная запись и подписка не нужны. Повторный `bi:setup` обновляет те же вопросы и демонстрационный dashboard, поэтому собственные эксперименты следует делать в их копиях.

## Расчёты и права

- Сохранённый вопрос «Метрики общего дашборда» считает факт, предыдущий период, интервальную и накопительную историю, разрезы по рынку/направлению/каналу. Суммы — BYN; сутки — Europe/Minsk; конец периода исключается.
- Формулы: выручка = сумма revenue; заказы = количество заказов; брак = defect / количество × 100%. Пустая сумма и счётчик — 0, пустая доля — null. План/сценарий остаётся правилом приложения и так подписан.
- Доступные метрики и подразделения определяются личной сессией. Подразделения, даты и все фильтры входят в locked-параметры подписанного сервером запроса. Руководители/сотрудники получают только разрешённые показатели своей области; финансовые значения не добавляются в их ответ.
- Результат имеет `source: "Metabase"` и `sourceInfo` с dataset, upstream, questionId, статусом и временами. Эти сведения доступны также в экспорте и каталоге метрик.
- Кэш на сервере — до 30 секунд с учётом источника, области и фильтров. Изменение fingerprint CSV обходит кэш и обновляет SQLite-снимок. Отказ источника оставляет другие KPI доступными, а метрики Metabase получают `—` и явное сообщение об ошибке; локальные значения под этим названием не подставляются.
- Время исходных данных пока является временем общего CSV-набора. Оно отдельно от времени снимка и запроса Metabase; это не подтверждение пофайловой свежести.
- Секрет/пароль остаются в игнорируемой `.data/`, права файлов 0600. Public sharing выключен. Старый signed-dashboard endpoint сохранён только для проверки исходного образца; UI его не использует.

В Metabase также остаются шесть первоначальных демонстрационных карточек. Приложение получает JSON из отдельного сохранённого вопроса и рисует собственный общий интерфейс. H2 хранит настройки Metabase для MVP; для эксплуатации нужен PostgreSQL и постоянное размещение.

## Проверки

`npm test` — вычисления, права, серверный источник, ошибки и отображение provenance. `CONTOUR_URL=http://<LAN-IP>:3000 npm run test:bi` — настоящие запросы Metabase через приложение для семи ролей, фильтры, история, пустые периоды, отсутствие секретов/localhost-зависимостей в ответах. Smoke входит локальными аккаунтами и оставляет обычные записи входа/выхода в аудите.

Общие известные пробелы проекта перечислены в `audit/2026-11-12-strict/report.html`; подключение BI не означает их исправления.
